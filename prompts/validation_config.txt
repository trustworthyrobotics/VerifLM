Active object:

Passive object:
- Name: {passive_object}
- Dimensions [x, y, z] in meters: {passive_dimensions}

Select exactly one validation mode:

- `settling`: Simulate the scene under gravity for a fixed horizon. Validate stability using the active object's final pose, system-defined penetration limits, and final contacts. Use this mode when the active object should settle into a stable, supported configuration.

- `geometric_only`: Do not advance the simulation. Validate only the proposed goal pose and its contacts. Use this mode for intentionally unsupported goals, such as holding a teapot in midair while pouring, where forward simulation would cause the object to fall.

Return exactly one valid JSON object with this schema:

  "validation_mode": "settling | geometric_only",
  "required_contacts": [
    "active_passive | active_table"
  ],
  "forbidden_contacts": [
    "active_passive | active_table"
  ],
  "xyz_relations": [
    {
      "axis": "x | y | z",
      "relation": "greater_than | less_than",
      "subject": "active",
      "reference": "passive"
    }
  ],
  "allowed_position_drift_fraction": [float, float, float] | null,
  "allowed_orientation_drift_deg": float | null,
  "reasoning": "brief explanation"

Rules:

1. Use only whole-object geometric relations and object-pair contacts. Do not refer to semantic parts such as handles, rims, slots, pegs, or spouts.

2. `required_contacts`:
   - These contacts must exist at the end of `settling`.
   - For `geometric_only`, they must exist at the proposed pose.
   - Return an empty list when no contact is clearly required.

3. `forbidden_contacts`:
   - During `settling`, reject the candidate immediately if any forbidden contact occurs at any timestep.
   - For `geometric_only`, reject the proposed pose if any forbidden contact exists.
   - Example: a dish intended to hang on a rack should not contact the table.
   - Return an empty list when no contact is clearly forbidden.

4. Never place the same contact in both `required_contacts` and `forbidden_contacts`.

5. Add an XYZ relation only when it is clearly and reliably implied by the instruction. Relations compare object-center coordinates in the world frame.
   - Example: placing a mug on a plate implies `active z > passive z`.
   - Example: placing a dish in or on a rack may imply `active z > passive z`.
   - Otherwise, return an empty list.

6. For `settling`:
   - `allowed_position_drift_fraction` specifies the maximum absolute final displacement along world x, y, and z, divided by the corresponding active-object dimension.
   - `allowed_orientation_drift_deg` specifies the maximum permitted angular difference between the proposed and final orientations.
   - Choose tolerances based on task sensitivity. A mug hanging from a rack may tolerate substantial rotation while settling, whereas a dish placed in a rack should tolerate much less rotation because a large change may indicate tipping.

7. For `geometric_only`, set both drift fields to `null`.

8. Do not invent contacts, relations, or constraints that are not clearly supported by the instruction. When uncertain, omit the constraint.

9. Output JSON only. Do not include Markdown, comments, or additional text.
